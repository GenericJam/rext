# rext — prototype architecture

- Date: 2026-07-20
- Status: accepted

## Context

Building a desktop sibling to mob. Desktop and mobile differ enough (packaging,
windowing, no OS-suspend of the runtime, no cross-compile-into-app-bundle) that
a separate framework is warranted rather than bending mob to fit. mob's core
programming model, however, is platform-agnostic and worth reusing.

## Decisions

1. **Copy mob's core, don't share a library yet.** rext copies mob's
   platform-agnostic model (screen→window GenServer, socket, renderer,
   theme/token resolution, the `Test` agent harness) rather than extracting a
   shared `beam_native_ui` package up front. A shared package is a later
   refactor, justified only if the duplication proves significant and enduring
   (rule of three). rext keeps these modules import-clean so extraction stays a
   move-files operation.

2. **Desktop paradigm, not mobile.** The unit of UI is `Rext.Window`; apps run
   many windows at once (many supervised GenServers). There is no navigation
   stack (mob's `stack`/`tab_bar`/`drawer`); "another view" is "another window".
   `Rext.App` declares `windows/0` (and, later, `menu/0`).

3. **Three packages from day one.** `rext` (runtime, ships in the app),
   `rext_dev` (run/connect/dashboard/MCP — dev-only, never a shipped
   dependency), `rext_new` (generator archive). rext_dev exists from the start
   because agent support — the connect/introspect/drive front door — is a
   day-one requirement, not deferrable. The runtime-side of the agent harness
   (`Rext.Test`, and later a native tree-walk) lives in `rext` so it's RPC-able
   on the running node.

4. **Render targets mirror mob.** SwiftUI on macOS (in-process, like mob iOS);
   Compose Multiplatform for Windows + Linux (like mob Android). The in/out of
   process choice for the Compose side (embed a JVM via JNI vs. a Kotlin process
   over a Port) is deferred; the render protocol is kept transport-agnostic so
   it stays open.

5. **Transport-agnostic render protocol, socket transport for the prototype.**
   `Rext.Renderer` turns a tree into a normalized JSON frame and knows nothing
   about the wire. `Rext.Bridge` owns the transport. For the prototype the macOS
   SwiftUI backend is an out-of-process child connected over a localhost TCP
   socket, 4-byte length-framed (`{:packet, 4}` on both ends). Events route back
   to the owning window; the render path is a cast (never a call) to avoid the
   transport-handler reentrancy trap documented in mob's CLAUDE.md.

## Why the socket transport (and not in-process NIF) for the prototype

macOS requires `NSApplication` to own the process main thread. A normal BEAM
already owns it, so a true in-process NIF host requires the Swift app to own
`main()` and boot an *embedded* ERTS as a guest thread — exactly what mob's
`mob_beam.m` does for iOS. That is weeks of ERTS-embedding work before anything
is visible. The socket transport proves the entire programming model + agent
harness now, and the Swift render/decode code and the whole Elixir core port to
the in-process host unchanged (only `Rext.Bridge` swaps sockets for NIF calls).

## Consequences / follow-ups

- **In-process NIF host** is the production next step for macOS: Swift owns
  `main()`, boots embedded ERTS (far more tractable on desktop than mob's mobile
  embedding — native arch, no App Thinning/SELinux/adb, unsigned OK for dev).
- **Agent harness verified over dist**: connect from a second node, read
  window tree/assigns, `Rext.Test.click/3` — all confirmed. A renderer-side
  screenshot for pixel verification is an additive step, not yet built.
- **GUI-session caveat**: a bare/`open`ed app will not display a window when
  launched from a shell detached from the Aqua login session (`screencapture`
  → "could not create image from display"; `open` → OSLaunchd Code=125). The
  data path (BEAM ↔ SwiftUI decode) is fully verified regardless; on-screen
  pixels require launching inside the user's GUI session.
- **rext_mcp**: `.mcp.json` generated by `rext_new` points at `rext_mcp.server`
  (not yet built). Fold MCP into rext_dev first; split `rext_mcp` out if it grows.
- **Deferred from prototype**: menus, multi-window demos, plugin mechanism
  (keep mob's, ship a fatter core), Port-based "language partners", packaging
  (.app/.dmg/MSI/AppImage), sigil/templates, state persistence.
